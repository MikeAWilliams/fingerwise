## F18-S01: A song change clears the last run

Story: [`F18-S01-song-change-clears`](../docs/features/18-retry-and-tempo/stories/F18-S01-song-change-clears.md)

Covers: AC1, AC2, AC3, AC4, AC5, AC6

What survives, found by reading the code (confirm while fixing): when the tune changes, the card stays mounted, so `SongOverlay` keeps its DOM. Its frame-loop effect (`SongOverlay.tsx`, the `useEffect` that calls `clear()`) returns early when `!running || origin === null`, so in the new flow's `ready` it never runs `clear()`. As a result (1) live feedback's settled fill and fault-mark paths, written with `setAttribute("d", …)` on per-row `<path>`s keyed by index, stay on the new song's lanes (AC1), and (2) the playhead `<line>`, whose `visibility` attribute was removed during the run, stays visible where it stopped. The summary, tuning, analysis, spots, `scored` and overrun all come from `timed` state, which the new flow's `start()` replaces, and scoring after the song clears its paths when `scored` goes back to null. Single note's message, fingering and head come from `single` state, and its trace effect clears on cleanup. AC2 and AC3 are expected to hold already; AC4 remounts the card (Settings unmounts it), so it is expected to hold too.

- [ ] Write the failing test first: in `tests/app/playhead.test.ts`, test a new pure `overlayRun(running, origin): "run" | "keep" | "clear"` from `src/app/playhead.ts`. It gives `"run"` while running with an origin, `"keep"` with an origin and not running (the summary keeps its fill, marks and stopped playhead), and `"clear"` with `origin` null (a fresh flow in `ready`, which is what a tune change gives). Run `bun run test tests/app/playhead.test.ts` and see it fail.
- [ ] Add `overlayRun` to `src/app/playhead.ts`. In `SongOverlay`'s frame-loop effect, branch on it: on `"clear"`, when `fill` is set (Tempo practice with judging), empty every fill and mark path, and always set the playhead line's `visibility` to `hidden`. Then return. On `"keep"`, return as now. On `"run"`, go on as now. Do not touch Single note's tone-trace paths: Single note has `fill` null, and its own effect owns its open paths. Without this guard, a clear could blank them while that effect's `written` cache thinks they are drawn.
- [ ] Check the other suspects against the code, and record what was found in Notes below: the overrun lane's `aspect-ratio` (`Staff.tsx`'s `extraHeight` effect), the readout text node, the `SongStaff` scroller's `lastRow`, the `useAnalysisBelow` state in `Card.tsx`, and Single note's message, fingering and trace on a tune change (AC3). For each real leftover, write a failing test first (a pure helper, as above), then fix it.
- [ ] AC5: in `tests/app/song-form.test.ts`, test that `chooseTune` returns null for the tune already chosen, if no test does yet. The `App` handler already does nothing on null.
- [ ] AC4: confirm in code that opening Settings unmounts the card (`!open &&` in `App.tsx`), so closing it with a new song mounts a fresh `SongOverlay`. The `overlayRun` fix also covers the first render, since the new flow is in `ready`.

Under **Tune list**, replace "a finished run's state goes with the old flow" with what a song change clears and how: the flow state through a fresh flow, and the overlay's drawn fill, marks and playhead through `overlayRun`'s `"clear"` in `ready`. ## Notes

- **S01 test without a DOM.** Components are not unit tested (no DOM in the test setup), and adding one would be a new dependency. So each leftover is reproduced by a failing test of the pure decision that let it survive (`overlayRun`), as `lanesShown` and `cardPhase` are. The leftover itself is checked by hand in `F18-checks.md`.
- **S02's played song.** `songSlotsMs` and `playbackSchedule` read `song.tempo` before their fallback, so a chosen tempo cannot be passed as a fallback. `App` passes the flows a copy of the chosen tune with `tempo` replaced (`withTempo`). The saved text, `songState` and the core are unchanged, which matches the design's "the core already takes the tempo as an input".
- **S02 defaults.** Choosing the tune's own entry saves `null`. A tempo equal to the tune's within 1e-9 is one entry. The load-time correction of `songTune` also resets `songTempo`, since a different tune's tempo should not carry over.
- **S03 tap reveal.** The design names a wrong note and the timed reveal. A tap reveal while the stream runs is a miss too, and it also listens for the retry: the card waits for a tap either way, and playing it right then moves on. Say so if a tap reveal should not listen.
- **S03 the window after a wrong retry note.** The tone tracker reports one tone per reset, so the flow resets it after each wrong note in the retry. The hold-off then also drops that note's tail.
