## F14-S01: Several tunes in the song text

Story: [`F14-S01-several-tunes`](../docs/features/14-tune-choice/stories/F14-S01-several-tunes.md)

Covers: AC1, AC2, AC3, AC4, AC5, AC6, AC7, AC8, AC9, AC10

- [x] `src/core/settings/index.ts`: new field `songTune: number` (the chosen tune's 1-based position) on `Settings` and `SettingsJson`, in `toSettingsJson`. `isValidSongTune(value)`: `Number.isInteger(value) && value >= 1`. `validateSettings`: a missing or invalid `songTune` resets alone to `defaults.songTune`. `parseDefaults`: throws `SettingsError("songTune must be a whole number of at least 1")` when it fails. The core module never parses ABC, so "past the last tune" is the app's job (below) (AC6).
- [x] `data/settings/defaults.json`: `"songTune": 1`, placed after `songAbc` (AC6).
- [x] Tests: in `tests/core/settings.test.ts`, the default, the strict parse (missing, 0, 1.5, "2", -1), old data without the field keeping every other field, each bad value resetting alone, and the round trip (AC6). Update `tests/data/settings-defaults.test.ts`, `tests/app/settings-store.test.ts` and `tests/app/settings-form.test.ts` fixtures wherever they list every field.
- [x] `src/abc/abcjs.d.ts`: type `TuneBook` (`new (book: string) => { header: string; tunes: { abc: string; startPos: number }[] }`) on the module, so the adapter can map warning lines. It comes from the same deep import, so ADR 0006's single-import rule still holds.
- [x] `src/abc/index.ts`, the result shape: `export interface ParsedTune { song: Song; notes: number; converted: number }` and `AbcResult = { ok: true; tunes: ParsedTune[] } | { ok: false; problems: AbcProblem[] }`, where `tunes` is non-empty and in text order. `AbcProblem` gains `tune?: number` (1-based position, AC3). It is set only when the text holds two or more tunes, so a one-tune text gives exactly today's problems (AC9).
- [x] `src/abc/index.ts`, the reading: move today's per-tune body (from `noteElements` to the converted count) into `readTune(text, tune, instrument, lineOffset): { ok: true; parsed } | { ok: false; problems }`, unchanged except as follows. `parseAbc`: keep the 10,000-character check on the whole text, with no tune (AC5). Delete the "Only one tune is supported" rejection (AC1). Call `parseOnly(text)` once, then `readTune` for each tune. Problems are gathered tune by tune, in tune order, each tagged with its tune when there are several, and `summed()` is applied once to the whole list. The "and N more problems" line carries the 11th problem's tune and line (AC2). The text passes only when every tune passes (AC1, AC2).
  - Positions: `startChar` offsets from abcjs are already counted in the whole text (checked with abcjs 6.7.2), so `locate(text, startChar)` gives whole-text lines. Notes are counted within each tune by its own `noteElements` (AC2).
  - Warning lines: abcjs counts a warning's line from the start of the tune's own text, and puts any `%%` directives from before the first `X:` ahead of it. With several tunes, build `new TuneBook(text)` and turn abcjs's line `w` for tune `i` into `locate(text, book.tunes[i].startPos).line + w - 1 - (directive lines in book.header)`. The column is unchanged. With one tune the mapping is the identity, so today's tests still hold. Before relying on it, assert in a test that `book.tunes.length === tunes.length` for the texts below (AC2).
  - A problem with no note to point at ("No notes found", the second-track "Only one voice", a `setUpAudio` throw) gives the line of that tune's `X:` (its `startPos`), not line 1, when there are several tunes.
  - The 500-note limit is checked per tune, at that tune's first note over (AC5).
- [x] `tests/abc/abc.test.ts`: update the existing `ok` expectations to `tunes[0]`. Replace the "more than one tune" rejection test. New `describe("several tunes (F14-S01)")`:
  - Two and three tunes: each tune's pitches, starts, beats, title, tempo and meter written out, plus `notes` and `converted` per tune (AC1, AC7).
  - A failing tune first, in the middle and last: its `tune`, its whole-text `line` and its `note` within the tune. Include a failing abcjs warning in tune 2 or 3, so the line mapping is tested (AC2).
  - More than 10 problems across tunes: the cut, and the tune on the summary line (AC2).
  - `X:` numbers that skip (1, 5, 9), repeat (1, 1) and run backwards (3, 2, 1): `tune` follows position (AC3).
  - Per-tune limit: one tune with 501 notes after repeats is reported at note 501 with its tune, and two tunes of 300 notes each pass (AC5). The 10,001-character text has no `tune` (AC5).
  - File header: a `%%` directive line and an `L:1/8` line before the first `X:`. Write out what abcjs does: per `abc_parse_book.js`, only `%%` lines reach the tunes and `L:`/`K:`/`M:` there are dropped. Check that warning lines stay right with the directive present.
  - Prose between tunes, after a blank line: abcjs ends a tune at the first blank line and ignores what follows up to the next `X:`, so no problem is expected. Write that out.
  - A one-tune text gives no `tune` on any problem (AC9).

## Notes

- Minor choices made here: the setting is named `songTune`. `AbcResult` becomes `{ ok: true; tunes }` rather than keeping a `song` field for the first tune. A problem carries a tune only when the text has two or more tunes. A past-the-end stored position is corrected and saved at load, as use song off already is.
- abcjs 6.7.2, checked while writing this breakdown: `parseOnly` gives one tune per `\nX:` and ends each tune at its first blank line, ignoring the prose that follows. Note `startChar`s count from the start of the whole text. Warning lines count from the tune's own text, with any `%%` directives from before the first `X:` placed ahead of it. Of a file header, only `%%` lines reach the tunes: an `L:`, `M:` or `K:` before the first `X:` is dropped without a warning. The S01 tests write this out, and the abc doc records it (design risks).
- Choosing a tune leaves keyboard focus on the list, so Space then opens the list instead of starting a run. That is the native behavior and does not break AC10. It is noted in the hand checks for the user's view.
